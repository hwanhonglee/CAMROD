[P0-A] 도로 폭, 차체 외곽과 sensor TF 실측
- 실제 정지/접촉 위치마다 lanelet ID, map XY, 좌우 도로 경계, 포장된 갓길,
  연석/낭떠러지와 실제 통과 가능 폭을 줄자 또는 레이저로 3회 측정한다.
- SLAM 그림 폭만으로 판정하지 않는다. map 폭과 실측 최소 폭의 차이를
  기록하고 planning 폭 `1.270 m`가 실제로 들어가는지 먼저 판정한다.
- front/rear/left/right body 외곽, 바퀴, 브래킷, 적재함, 케이블과 회전 swept
  envelope를 측정해 현재 ordinary-motion stop body 및 10 cm margin과 대조한다.
- `map -> odom -> robot_center_link -> robot_base_link`가 단일 TF tree인지,
  `robot_base_link`가 후륜 차축 호환 frame X `-0.443 m`인지 확인한다.
- GNSS rover X/Z, moving-base XYZ, baseline 방향/길이와 receiver position
  reference도 함께 측정한다. 현재 확인값은 rover Y `+0.45 m`뿐이다.
- 합격: 지도/차체/센서 값의 출처와 오차가 기록되고, 정상 lane에서 body와
  planning boundary가 실제 폭 안에 있으며 frame publisher 중복이 없다.

[P0-B] GNSS, IMU와 20 Hz localization 주행 검증
- 시작 시 두 GNSS의 NAV-PVT/NAV-RELPOSNED rate, iTOW, flags 131/311 Fixed,
  RTCM owner/rate와 IMU 약 100 Hz를 기록한다.
- HH_260807 launch의 `5 Hz`에서 먼저 `1 -> 2 km/h` 왕복 주행한다. GNSS,
  dual heading, IMU, wheel odom, EKF/final pose, cmd_vel, steering/wheel feedback를
  한 rosbag에 기록한다.
- PVT/RELPOSNED iTOW가 200 ms이고 rover와 moving-base가 동일 주기인지,
  Fixed 유지율과 serial/RTCM 대역폭이 악화되지 않는지 확인한다. 손실이 있으면
  1 Hz를 통제된 비교군으로만 시험하고 5 Hz 실패 근거를 함께 기록한다.
  localization/controller는 우선 `20 Hz`를 유지하고 측정 없이 다시 올리지 않는다.
- final pose `>=18 Hz`, 지속 age `<500 ms`, 20 cm 초과 jump 0, localization
  INVALID 0, 좌우 중심선 반복 교차 0을 합격 기준으로 사용한다.
- timestamp가 같은 GNSS와 EKF 예측의 XY innovation을 저장한다. `0.30 m`
  절대 gate는 bag replay로 startup/reacquisition과 정상 회전을 통과한 뒤에만
  적용한다. `pose0_rejection_threshold=3.0`을 `0.3`으로 바꾸지 않는다.
- dual-GNSS heading의 현재 `pose1_rejection_threshold=1000`은 moving bag의
  normalized innovation으로 finite sigma 후보를 검증한다.
- IMU startup port `0x13` 오류와 재기동 후 Fixed 미획득이 재현되면 P0 FAIL이다.

[P0-C] 왕복 서비스, state와 연속 mission 수명 검증
       [SIM 10/10 (9 FULL OUTBOUND), FIELD-PENDING]
- B1-B10에서 다음 전체 순서를 사이트를 바꿔 최소 3회 연속 수행한다.
  `drop-zone/charging -> campsite route -> CRAB_IN -> ROTATE_180 ->
  WAITING_FOR_RETURN_REQUEST -> 사용자 RETURN -> CRAB_OUT -> return route ->
  drop-zone alignment -> parking -> WAITING_FOR_CHARGING -> CHARGING ->
  DEPARTING_CHARGER -> 다음 campsite`
- 사이트 도착 즉시 자동 RETURN하지 않아야 하며, 사람이 하역하는 동안
  WAITING_FOR_RETURN_REQUEST와 zero final cmd_vel을 유지해야 한다.
- manual engage와 UI destination 모두 MOVING/DRIVING 상태를 표시해야 한다.
- cancel은 OPERATOR_STOPPED로 전환되고 5초 동안 goal/path/nonzero cmd_vel이
  자동 재생성되지 않아야 한다. planning의 정상 maneuver handoff cancel은
  system warning으로 고정되지 않아야 한다.
- B11-B13은 `CRAB_IN -> WAITING_FOR_RETURN_REQUEST` arrival까지만 시험한다.
  현장 복귀 geometry가 정해질 때까지 on-site zero-turn과 자동 RETURN은 금지한다.
- 합격: node/bringup restart 없이 3회 이상의 site-return-charge-next-site가
  순서대로 완료되고 state, motion owner와 최종 command가 일치한다.
- SIM 기준 B1-B10은 `2210.611 s`, restart 0으로 10/10 통과했다. cycle 1은
  B1 route endpoint에 준비한 site handoff이고, cycle 2-10은 charger departure부터
  outbound/RETURN/parking/charging까지 모두 실행했다. cycle 5 장애물
  stop/clear/resume도 통과했다. 실제 CAN 충전, 실제 하역 대기, 사람의 RETURN
  입력으로 같은 판정을 다시 수행해야 이 항목을 닫는다.

[P0-D] 장애물 정지, 넓은 lane 우회와 boundary 회복 [SIM 부분 PASS, FIELD-PENDING]
- 동적 장애물은 즉시 최종 cmd_vel을 0으로 만들고, 제거 후 fresh clear window
  뒤 기존 mission을 재개해야 한다.
- 20초 지속 장애물은 실제 연속 폭 `>=2.50 m`, 좌우 clearance 각각
  `>=0.60 m`, fresh lanelet grid를 만족하는 위치에서만 SmacLattice fallback
  path를 생성해야 한다. 좁은 lane/stale/outside-map은 우회를 거부하고 정지한다.
- planning margin 한쪽만 cost 100에 닿게 해 반대 crab, straight reverse,
  reverse-yaw 단계가 projected full-footprint를 매번 확인하는지 기록한다.
- recovery 제한은 최종 `0.18 km/h`, raw `0.10 m/s`, yaw `<=0.10 rad/s`,
  누적 `<=12 deg`, 이동 `<=0.40 m`, 시간 `<=10 s`다.
- 같은 contact region의 release는 최대 50회로 제한하고, signed forward
  progress가 `0.75 m`를 넘으면 새 region으로 reset한다. budget에 도달하면
  같은 방향 Nav2 재개는 막되, overlap이 단조 감소하고 swept physical body와
  endpoint planning boundary가 모두 clear인 탈출 후보는 계속 허용해야 한다.
- virtual lanelet의 physical-body cost 100에서도 ordinary motion은 0이어야 하며,
  현재 overlap이 단조 감소하고 swept body/endpoint planning 검사를 모두 통과한
  inward escape만 허용한다. 실제 장애물, 사람, interlock은 계속 fail-closed다.
- 합격: margin 또는 virtual-body 접촉에서는 위 조건의 안전 방향으로 빠져나와
  원 mission을 계속하고, 후보가 없거나 우회 공간이 부족하면 정지한다.
- historical map-v17 B2 margin recovery는 3/3 통과했고, 약 3.00 m lane의 centered
  obstacle은 Smac preflight no-path 1회 뒤 정지 유지/제거 후 재개를 통과했다.
  최종 B1-B10 endurance에서는 B2-B10 margin hold 9회가 모두 recovery motion,
  1.5 s release, 원 mission 계속 주행으로 끝났고 retry latch는 0이었다.
  현재 지도에는 active footprint+inflation으로 성공 우회를 주장할 만큼 넓은
  road lanelet이 없으므로, 실측된 넓은 lane의 성공 회피는 계속 미완료다.

[P1-E] Radar TF/노이즈 및 후방 카메라 rate
- 새 radar 거치대 설치 후 각 채널 XYZ/RPY/frame을 `robot_center_link` 기준으로
  측정하고 설정/진단 metadata와 동기화한다.
- 주변을 완전히 비운 7채널 15분 raw를 저장하고 거리별 시험 장애물을 한 채널씩
  배치한다. self-return과 실제 장애물을 분리하기 전 fixed exclusion을 추가하지 않는다.
- rear raw/camera_info/compressed rate를 production 부하에서 재측정한다. raw
  목표는 10 Hz이며 기존 실측 3.633 Hz의 CPU/driver/encode 원인을 구분한다.
- 합격: radar 실제 장애물을 가리지 않는 noise 정책과 rear 10 Hz, AprilTag
  pose/rate, publisher 중복 0을 확인한다.

[P1-F] Jetson container CPU/GPU/PSS와 반복 종료
- 최종 대상은 ARM64 8코어/16 GB RAM이다. AMD64 수치는 구현 전후 비교와
  계측 절차 검증에만 사용하고 Jetson 합격값으로 전용하지 않는다.
- 같은 mission에서 production container와 all-standalone을 각각 5분 x 3회
  측정한다. 개발용 VS Code/브라우저와 다중 `topic hz` 부하는 분리한다.
- 전체/프로세스 CPU, GPU, RSS/PSS, camera/LiDAR/radar/localization/control rate,
  command latency, startup-to-SYSTEM OK를 기록한다.
- checker/Nav2/system-core, camera/YOLO, rear camera/AprilTag, LiDAR 처리 경로를
  fault domain별로 비교하고 mission/cancel/start/stop 10회를 수행한다.
- 운영 비교는 LiDAR cost grid OFF, DDS-SHM OFF, WebKit 기본으로 시작한다.
  Chromium/`auto`는 별도 대안 A/B이며 host AMD64 결과를 Jetson 결론으로 쓰지 않는다.
- 관리자 telemetry를 GNSS -> proximity -> camera -> trajectory -> perception ->
  safety 순으로 30분 반복 전환한다. backend CPU/PSS, 전체 GPU, JSON payload,
  카메라 frame pacing, 각 view의 `4-11`개 동적 subscription 해제, 메모리 증가와
  재진입 직후 Hz 표시를 기록한다.
- 합격: crash/-11/-9/forced kill/잔여 process 0, 필수 topic rate 유지, 자원
  절감 수치와 fallback 조건이 기록된다.

[P1-G] UI/Guest UI/voice 운영 표시
- Robot UI와 Guest UI에서 destination, RETURN, cancel, charging recall을 각각
  실행하고 같은 `/service/state` 의미를 표시하는지 확인한다.
- INITIALIZING, READY, MOVING_TO_SITE, SITE_ENTRY, WAITING_FOR_RETURN_REQUEST,
  RETURNING_TO_DROP_ZONE, WAITING_FOR_CHARGING, CHARGING, DEPARTING_CHARGER,
  SAFETY_STOP, OPERATOR_STOPPED의 순서와 음성을 기록한다.
- WARN/DUMMY 센서만으로 INITIALIZING에 영구 고정되지 않아야 하고, 실제 ERROR는
  숨기지 않아야 한다.
- 관리자 6개 telemetry view에서 GNSS/IMU/radar/LiDAR/camera/map/path/obstacle/
  gate topic 이름과 실제 `ros2 topic info` publisher를 대조한다. 전·후방 raw
  camera는 각각 10 Hz, rear monitoring JPEG는 2 Hz 계약으로 구분하고, 화면의
  frame age/rate가 물리 probe와 일치하는지 확인한다.
- 합격: keypad/터치 지연, 중복 WebSocket command, 중복/역순 음성, 잘못 고정된
  system warning 없이 Robot/Guest UI가 동일한 운행 의미를 제공한다.
