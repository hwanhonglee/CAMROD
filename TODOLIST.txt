CAMROD v2.1.0 실차 확인 목록
작성일: 2026-07-29 (Asia/Seoul)

범위
- 이 파일에는 v2.1.0 코드/설정/문서 반영 후에도 실제 로봇에서 확인해야
  하는 항목만 남긴다.
- 사용자의 요청에 따라 이번 마무리에서는 실제 bringup, 센서 구동, engage,
  주행 테스트를 실행하지 않는다.
- 빌드, 단위 테스트, launch/config 정적 회귀 테스트는 릴리스 전에 실행한다.

[P0] 1. radar 비활성화 상태의 cost 완전 차단
- 실행:
  ros2 launch camrod_bringup bringup.launch.py enable_radar:=false
- 확인:
  1) sen0592_radar_node가 없어야 한다.
  2) FRONT1/FRONT2/LEFT1/LEFT2/RIGHT1/RIGHT2/REAR가 모두 DUMMY DATA로
     표시되어야 한다.
  3) LEFT2는 0.801 m / max_range 0.800 m 형태의 no-target이어야 한다.
  4) radar_cost_grid 로그가 7채널 dummy-state cost 차단을 표시해야 한다.
  5) /sensing/radar/obstacle_evidence는 "clear"이어야 한다.
  6) cmd_vel 정지 사유에 radar가 없어야 한다.
- 합격 기준:
  10분 동안 radar obstacle evidence active 및 radar 유래 cost stop 0회.

[P0] 2. 전방 카메라 + YOLO component 실차 회귀
- 배경:
  기존 17:01/16:58 로그에서는 물리 전방 카메라와 손상된 1x1 dummy JPEG가
  동시에 입력되어 YOLO compressed callback의 OpenCV 예외로 container가
  SIGABRT(-6) 종료됐다.
- 확인:
  1) /dev/video0 물리 publisher는 정확히 1개여야 한다.
  2) component 사용 중 front_camera dummy는 없어야 한다.
  3) 전방 image_rect/compressed와 camera_info가 지속 발행되어야 한다.
  4) /perception/camera/detections_2d가 발행되어야 한다.
  5) 유효하지 않은 compressed frame을 별도로 주입해도 YOLO가 종료되지
     않고 원인을 포함한 throttled WARN만 출력해야 한다.
  6) component ProcMaps/ldd에서 OpenCV 4.8(/usr/local)과 4.5(system 또는
     workspace vendor)가 동시에 로드되는 현재 ABI 혼재를 제거하거나
     안전성을 입증한다. 물리 front NVJPEG 각 frame의 payload size와
     decode 성공도 별도로 확인한다.
- 합격 기준:
  component container와 YOLO가 5분 이상 생존하고 SIGABRT/재시작 0회.

[P0] 3. 후방 카메라 실측 rate
- 확인:
  /dev/video1, /sensing/camera/econ_rear/image_raw,
  /sensing/camera/econ_rear/image_raw/compressed, camera_info를 확인한다.
- 합격 기준:
  raw는 설정 10 Hz에 근접하고 compressed monitoring은 약 2 Hz.
  낮은 FPS 경고는 "FPS low"로 나와야 하며 "Encoding mismatch"로
  잘못 표시되면 안 된다.

[P0] 4. lanelet 전체 footprint 정지 원인 확인
- 배경:
  최신 17:01 radar-off 로그의 실제 정지는 radar가 아니라
  lanelet_footprint_cost였고 17:04:21~17:06:03 사이 46회 발생했다.
- 확인:
  완전히 비어 있고 정상 route 내부인 위치에서 radar-off로 재현한다.
  정지 순간의 localization pose, /platform/robot/planning_boundary,
  /map/cost_grid/lanelet, map 원점/해상도/해당 cell을 함께 저장한다.
- 합격 기준:
  planning boundary 전체가 허용 corridor 안이면 주행 가능하고, 어느 한
  점이라도 off-lane cost 100에 닿으면 계속 정지한다.
- 주의:
  좌표/맵 정렬 증거 없이 footprint guard나 threshold를 낮추지 않는다.

[P1] 5. radar 7채널 clear-area 및 장애물 분리 측정
- 모든 센서 주변을 완전히 비운 상태로 7채널을 동시에 15분 측정한다.
- 기존 fixed_return_bands 안의 반복 chassis/floor return과 실제 장애물을
  각 거리에서 분리해 기록한다.
- LEFT2 0.365~0.382 m, RIGHT1 0.391~0.406 m, RIGHT2 0.362~0.369 m는
  주변 장애물이 있던 환경의 값이므로 현재는 예외 처리하지 않는다.
- 합격 기준:
  새로운 exclusion은 완전한 clear-area에서 반복 재현된 좁은 대역만
  검토하며, 동일 거리의 실제 장애물 가림 위험을 문서화한다.

[P1] 6. goal -> path -> cmd_vel -> 실주행 승인
- 가까운 goal과 먼 goal을 각각 수동 RViz 및 UI에서 생성한다.
- global path, local path, /control/cmd_vel_raw, /control/cmd_vel,
  platform drive enable, engage 상태를 한 타임라인으로 저장한다.
- 합격 기준:
  path와 cmd_vel이 지속 생성되고 장애물이 있는 동안은 latch 정지,
  제거 후 설정된 clear window 뒤에만 해제된다.

[P1] 7. planning 경로 품질과 goal 정책
- 수동 RViz goal은 어느 방향/위치에서도 planner 입력을 받아야 한다.
- UI goal에는 lanelet snap, 접근 방향, 운영 규칙이 적용되어야 한다.
- 장거리 ABORT와 구불구불한 경로를 planner별로 재현하고 변경 전/후
  path length, curvature, abort reason을 비교한다.

[P1] 8. full bringup CPU 프로파일
- 실제 goal/path/cmd_vel 계산 상태에서 5분 이상 측정한다.
- 프로세스별 CPU, 전체 CPU, GPU, RAM, cost-grid/topic rate, camera/YOLO
  rate를 같은 시각으로 저장한다.
- RViz, 경량 WebKit UI, UI window off를 각각 비교한다.
- 합격 기준:
  가장 큰 부하 프로세스와 절감 전/후 수치를 명시하고 센서/안전 topic
  rate가 허용 범위 아래로 떨어지지 않아야 한다.

[P2] 9. voice 및 수동 engage 상태 시퀀스
- 먼저 현재 voice 입력과 실제 발화 순서를 코드/rosbag으로 표로 만든다:
  /service/state, /planning/nav_status, manual/mission engage, localization mode,
  system/module health -> voice event -> 발화 문구.
- "준비 완료"의 조건을 명시한다. 최소한 필요한 센서/TF/map/localization,
  planning/action server, control gate, platform 상태가 준비되고 수동 또는 UI
  goal을 안전하게 받을 수 있어야 한다.
- 위 준비 조건 전에는 "drop-zone으로 복귀 중"이나 "preparing" 대신
  "초기화 중"을 표시·발화한다. 준비 완료 후에만 1회 준비 완료를 알린다.
- 수동 RViz goal + engage도 UI mission과 같은 상태 어휘와 순서
  (goal 접수 -> 경로 준비 -> 주행 -> 장애물/경계 정지 -> 도착)를 사용한다.
- 초기 부팅, 센서 지연, localization 재획득, manual goal, UI goal, 재engage
  각각의 중복/역순/누락 발화를 회귀 테스트한다.
- 합격 기준:
  실제 이동 명령이나 유효 mission이 없는데 복귀/주행 음성이 먼저 나오지
  않고, 준비되지 않은 상태를 "준비 완료"라고 말하지 않는다.

[P2] 10. GNSS/IMU 물리 포트 최종 확인
- 이번 변경에는 GNSS/IMU 포트 YAML 변경이 없었다.

[P0] 11. lanelet 밖으로 이탈 후 시나리오 자동 회복
- 쉬운 설명:
  로봇이 차선 경계를 밟으면 기존에는 브레이크만 잡고 "왜 멈췄는지"와
  "어느 방향으로 가다가 멈췄는지"를 복구 과정이 끝날 때까지 보존하지
  못했다. 이제 최초 진행 방향을 기억하고 ROUTE_SAFETY_HOLD를 표시한다.
  로봇 전체가 다시 안전한 차선 안에 들어왔다는 최신 증거가 1초 동안
  유지되어야 정지를 풀며, Nav2가 그 사이 ABORTED됐으면 원래 목적지를
  최대 2회까지만 다시 요청한다.
- 코드/설정/테스트 기록:
  - 보존 상태 정책: camrod_control/include/camrod_control/route_safety_recovery.hpp
  - lanelet 재확인: camrod_control/src/motion_cost_stop.cpp
  - 상태/command_enabled: camrod_control/src/cmd_vel_safety_gate_node.cpp
  - 동일 goal 재발행: camrod_planning/src/goal_snapper_node.cpp
  - 설정: cmd_vel_safety_gate.yaml, goal_snapper.yaml의 package/bringup 양쪽
  - 테스트: test_control_policies.cpp, test_route_goal_recovery.cpp
- 소프트웨어 반영 상태 (2026-07-29, post-v2.1.0, 실차 판정 대기):
  1) cmd_vel gate가 최초 lanelet 위반 방향/원인을 보존하고
     /control/command_enabled=false,
     /control/cmd_vel_safety_gate/status=ROUTE_SAFETY_HOLD를 발행한다.
  2) 원래 진행 방향의 fresh lanelet grid/pose/full-footprint가 1.0초 동안
     연속 clear일 때만 hold를 해제한다. stale/missing/frame mismatch는 clear로
     인정하지 않는다.
  3) Nav2가 이 hold 중 ABORTED인 경우에만 gate ENABLED 0.5초 후 동일 snapped
     goal/source를 재발행한다. goal당 최대 2회이며 일반 planning 실패나

[P0] 13. lanelet 중심선 횡방향 정렬 overshoot/제어 지연
- 쉬운 설명:
  상위 제어기가 "이제 반대쪽으로 조향"이라고 바꿔도 실제 Ranger 바퀴는
  한 번에 돌아가지 못한다. 기존에는 바퀴가 아직 이전 방향인데도 이동
  속도는 그대로 나가 중심선을 지나칠 수 있었다. 이제 목표 바퀴 각도와
  실제로 제한되어 전달되는 바퀴 각도의 차이가 크면 이동 속도를 줄이고,
  차이가 0.35 rad 이상이면 병진 속도를 0으로 만든다. 바퀴가 새 방향에
  가까워지면 속도가 선형으로 복원된다.
- 코드/설정/테스트 기록:
  - 속도 비율 정책: steering_transition_policy.hpp
  - Ackermann/parallel 적용 및 부호 처리: ranger_messenger.cpp
  - 설정 전달: ranger_driver.yaml package/bringup, ranger.launch.py
  - 테스트: 큰 조향 지연 정지, 중간 선형 비율, 기능 비활성 호환성
  - 미수정: 실차 시간값이 필요한 lateral 예측, gain, hysteresis
- 소프트웨어 반영 상태 (2026-07-29, 부분 완화, 실측/제어 보정 대기):
  1) Ranger의 최종 parallel/Ackermann steering 부호를 먼저 확정한 뒤
     0.5 rad/s rate limit을 적용하도록 순서를 고쳤다.
  2) 목표-제한 steering 오차가 0.05 rad 이하면 100% 속도, 0.35 rad 이상이면
     0%, 그 사이는 선형 scale을 적용한다. 바퀴가 이전 방향인 동안 새
     병진 속도가 먼저 나가 중심선을 더 지나치는 현상을 줄이는 driver
     계층 완화이며 unit test를 추가했다.
  3) full-footprint cost 100 guard와 boundary threshold는 변경하지 않았다.
  4) 아래 pose->controller->gate->platform 실측이 없으므로 lateral 위치 예측,
     부호반전 hysteresis, controller gain/ratio는 임의로 변경하지 않았다.
     좌/우 실차 수렴 기준까지 통과해야 최종 완료다.
- 실차에서 지금 할 일:
  1) map에서 충분히 넓고 직선인 lanelet을 선택한다. 중심선 기준 왼쪽과
     오른쪽의 작은 offset에서 각각 별도 run을 수행하되 yaw 오차는 작게 둔다.
  2) recorder와 bringup.log가 실행 중인지 확인하고 저속 centerline 정렬을
     시작한다. `/rosout`의 `steering transition limits velocity` 로그에는
     mode, target, limited, scale이 함께 남아야 한다.
  3) target-limited 조향 오차가 0.35 rad 이상인 샘플에서는 scale 0,
     0.05 rad 이하에서는 scale 1인지 확인한다. 중간값은 0과 1 사이에서
     선형으로 변해야 한다.
  4) rosbag의 localization pose, raw/final cmd_vel, `/actuator_state`,
     `/platform/status/wheel` stamp로 pose->controller->gate->wheel 구간별
     지연을 계산해 FIELD_RESULT.txt에 적는다.
  5) 왼쪽/오른쪽 시작 모두에서 중심선을 반복 교차하지 않고 cost 100에
     닿지 않은 채 수렴해야 PASS다. 한쪽만 성공하면 전체 항목은 FAIL이다.
  6) 실패해도 이번 현장에서 footprint threshold를 낮추지 않는다. 측정한
     지연과 좌/우 오차를 근거로 다음 변경에서 lateral prediction, gain,
     hysteresis 중 한 계층만 선택해 조정한다.
- 재현:

  남은 상태에서 centerline 복귀 제어를 수행한다.
- 현재 문제:
  조금 전진하며 아주 작게 회전하면 충분하지만 pose->controller->gate->
